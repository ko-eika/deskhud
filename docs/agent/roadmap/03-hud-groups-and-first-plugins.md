# HUD 分组与首批正式插件实施计划

状态：实施中（第一、二阶段已完成）
计划顺序：HUD 组基础能力 → 系统插件 → 便签插件  
当前基线：DeskHud 0.9.9 / engine 0.9 / Guest API 4

## 目标

在不破坏“每屏一个 HUD 合成窗、同层绘制”的前提下，将现有静态
`plugin_id + contribution_id` HUD 模型扩展为可组合、可实例化的模型，并以两个正式
内置插件验证它：

1. 用户可以将来自不同插件的 HUD 条目放进同一个 HUD 组，并在组内排版；
2. 系统插件提供真实的系统与应用性能数据；
3. 便签插件可以创建多个内容彼此独立的便签 HUD。

本计划不包含演示插件的删除或迁移；该工作由维护者在需要时单独处理。

## 总体模型

HUD 定义、HUD 实例和 HUD 组必须分离：

```text
Plugin / HudContribution（定义）
             │
             ▼
HudInstance（实例：配置、开关、独立身份）
             │
             ├── 未分组：使用自己的屏幕布局
             └── HudGroup：使用组布局 + 组内布局
```

建议的中性数据形状：

```rust
struct HudSourceId {
    plugin_id: String,
    contribution_id: String,
}

struct HudInstance {
    id: String,
    source: HudSourceId,
    enabled: bool,
    config: HudInstanceConfig,
    layout: HudSlotLayout,
}

struct HudGroup {
    id: String,
    name: String,
    enabled: bool,
    layout: HudSlotLayout,
    arrangement: HudGroupArrangement,
    children: Vec<String>,
}
```

- `HudContribution` 是插件提供的能力定义，不再兼任用户实例。
- `HudInstance.id` 由宿主生成并稳定落盘；布局、配置和分组引用均以实例 ID 为主键。
- 现有静态条目在读取时映射为确定性的默认实例，以保留当前开关和布局语义。
- 分组操作应以“HUD 条目/实例”为单位，而不是以插件为单位；一个插件可能贡献多条 HUD。组的创建、成员调整和删除统一留在 HUD 布局模式，不放进插件设置页。
- 第一版一个实例最多属于一个组，禁止嵌套组，避免循环引用与不明确的布局所有权。

## 第一阶段：HUD 组基础能力

### 1.1 契约与持久化

- [x] 在 `deskhud-engine` 定义平台无关的 HUD 来源、实例身份、帧上下文与组内布局语义。
- [x] 在 `deskhud-ui` 增加 `HudInstance` / `HudGroup` 偏好模型；组名、成员顺序、布局方式、间距、内边距和对齐方式可落盘。
- [x] 为旧的 `plugin_id + contribution_id` 开关和布局提供一次性、确定性的默认实例映射。
- [x] 定义未知插件、缺失 contribution、重复成员、损坏实例和孤儿组的恢复规则；单项损坏不得阻止其余 HUD 加载。
- [x] 明确实例 ID 的生成、复制与删除规则；不得以用户可修改的标题作为主键。
- [x] 按 `docs/versioning.md` 评估 engine 兼容族变化；只有实际修改 Guest/WIT ABI 时才递增 `api_version`。

1.1 落实规则：

- 旧定义的默认实例 ID 由完整 `plugin_id + contribution_id` 长度编码生成；迁移幂等，旧开关、屏幕布局和视觉值复制到实例，标题不参与身份。
- 新建实例、复制实例和新建组分别从偏好文件内尚未占用的 `instance:<n>` / `group:<n>` 顺序分配；复制品默认不入组。删除实例只删除目标实例并清除全部组引用；删除默认实例会记录来源抑制项，避免启动时重建。删除组保留成员并使其回到未分组状态。
- 插件或 contribution 暂时缺失时保留实例及组关系；恢复后按来源重新绑定。加载损坏数组时逐项反序列化，单项错误只丢弃该项。重复实例、重复组和跨组重复成员保留首次出现；悬空成员引用移除，空组继续保留。
- 本阶段仅增加原生 Rust 契约及宿主持久化，没有修改 Guest/WIT ABI，因此 `api_version` 保持 4；产品已处于 `0.9` 兼容族，`ENGINE_COMPAT_FAMILY` 与清单统一为 `0.9`。

### 1.2 组合与渲染

- [x] 将运行态收集链改为“解析活动实例 → 取得各实例帧 → 应用组内布局 → 应用组屏幕布局”。
- [x] 第一版支持横向、纵向和网格排列，以及间距、内边距和起始/居中/末端对齐。
- [x] 组作为一个虚拟 HUD 槽参与显示器选择、移动、缩放和视觉效果；成员不再同时使用独立屏幕坐标。
- [x] 组内对子帧执行中性坐标变换和裁剪，不让插件接触 egui、窗口句柄或 OS 类型。
- [x] 继续满足启用条件：HUD 总开关 ∧ 插件开关 ∧ 实例开关 ∧（若有）组开关。
- [x] 保持运行态每屏一个合成窗、同层绘制，禁止为每个组或成员创建独立 HUD 窗口。

1.2 落实规则：

- engine 只接收宿主测量后的逻辑尺寸，并输出组自然尺寸、成员逻辑矩形和裁剪矩形；横向、纵向与网格算法均不依赖 egui 或平台类型。
- 运行态先按稳定实例 ID 解析来源并请求 `hud_frame_for_instance`；暂缺来源不渲染但不删除配置。已入组实例只由所属组产生虚拟槽，组关闭时不会退回独立坐标。
- 虚拟组槽使用组自身 `HudSlotLayout` 选择显示器和定位；组的 `size` 使用实际逻辑像素且不设宽高上限。成员顺序、间距、内边距及对齐只影响组内逻辑坐标。egui 在同一 HUD 合成窗中解释成员变换并裁剪到组内容区域。
- 插件设置页继续负责 contribution 开关；组的创建与编辑由 1.3 的 HUD 布局模式承载。

### 1.3 布局模式中的分组与编辑

- [x] 第一步先拆分 `crates/apps/deskhud-egui/src/views/hud/drawing.rs`，参照 `views/setting/drawing/` 的做法改为职责单一的 `drawing/` 模块目录；拆分阶段只整理代码结构，不改变现有 HUD 绘制、布局编辑、偏好写入和窗口行为。
- [x] 插件设置页不提供 HUD 组的创建和管理；HUD 布局模式是组操作的唯一入口。
- [x] 在 HUD 布局模式中右击唤出菜单，并通过菜单创建、重命名和删除虚拟组。
- [x] 选中组时打开组调整窗口，在其中统一调整组的大小、位置、布局方式及其它组属性。
- [x] HUD 可以直接拖入组内，并在组内移动、排列或移出。
- [x] 组内支持自由布局，以及横向、纵向、网格等自动布局方式。
- [x] 组内的单个 HUD 可以独立选中，并使用 HUD 调整窗口修改自身样式。
- [x] 组、组内布局和成员样式均持久化，重启后恢复。
- [x] 布局编辑器提供信息树/活动树、对齐辅助线、位置/尺寸重置及应用/放弃布局会话。
- [x] 所有新增用户可见文案补齐现有中英文 gettext 目录与缺键回退，并复用现有 HUD 布局编辑器的视觉和交互风格。

1.3 做法：

- 先完成 `drawing.rs` 的纯重构并单独验证，再开始组选择、右键菜单、拖放和组调整窗口。目标结构由 `drawing/mod.rs` 负责绘制流程编排，其余模块分别承载布局画布与交互、调整窗口、位置与大小控件、视觉效果与阴影控件、HUD 内容绘制以及共享控件；模块间只暴露完成编排所需的最小接口。
- 布局模式同时支持选择未分组 HUD、虚拟组和组内 HUD；根据当前选择打开对应的调整窗口。
- 组调整窗口负责组自身的位置、尺寸和布局参数；HUD 调整窗口负责当前 HUD 的大小与视觉样式。
- 自由布局允许成员在组内直接拖动；自动布局由组按照所选方式排列成员。
- 将 HUD 拖入或移出组时直接更新成员关系和布局；一个 HUD 实例最多属于一个组，组不嵌套。
- 组和成员继续在所属显示器的同一个 HUD 合成窗中绘制，不为组或成员创建额外窗口。

### 第一阶段验收

- `drawing.rs` 已拆成职责清晰的 `drawing/` 模块，原有绘制与布局编辑行为保持不变，并已通过格式化、测试、workspace check 和 clippy。
- 来自两个不同插件的 HUD 实例可以在布局模式中通过拖放加入同一组，并按自由、横向、纵向或网格模式排列。
- 用户无需进入插件设置页即可通过布局模式的右键菜单创建和管理组。
- 组的位置、大小和布局均可在组调整窗口内完成。
- 组内成员可以单独选中、移动和调整样式。
- 组、成员关系、组内布局和成员样式重启后保持。
- 禁用任一层开关后对应内容立即消失，重新启用后状态和布局恢复。
- 插件暂时缺失时配置不会崩溃或错误绑定到其他插件；插件恢复后成员关系可恢复。
- 未分组的现有 HUD 在升级后继续按原位置和开关显示。

## 第二阶段：系统与应用性能插件

插件建议命名为 `hud.deskhud.system`，以官方内置原生 Rust 插件实现真实数据闭环。

### 2.1 数据采集边界

- [x] 建立缓存式采样器，按独立周期刷新数据，不在每个绘制帧执行昂贵的系统查询。
- [x] 第一批提供系统 CPU 使用率、内存已用/总量、DeskHud 进程 CPU 和内存。
- [x] 增加可选的应用进程 HUD：按稳定选择信息定位进程，处理进程退出、重启、同名进程和权限不足。
- [x] 采样结果转换为平台无关快照；engine、包契约和 HUD 帧中不得出现 OS 专有类型。
- [x] 采集失败或暂不可用时显示中性不可用状态，不阻塞渲染线程。
- [x] 后续再评估网络速率、磁盘吞吐、GPU 和温度；不把平台覆盖不一致的指标作为第一批验收前置条件。

### 2.2 HUD 与视觉

- [x] 独立贡献“系统 CPU”“系统内存”“DeskHud 进程”和“应用进程”四类 HUD 定义。
- [x] 根据需要向 `HudVisual` 增加平台无关的进度条和折线/历史曲线原语，并设置节点、历史长度和数值校验上限。
- [x] 为刷新周期、显示单位、是否显示标签等选项提供通用配置声明。
- [x] 为插件、HUD 条目、配置项和不可用状态补齐中英文包内 i18n。
- [x] 系统 HUD 可以作为普通实例加入第一阶段实现的任意 HUD 组。

### 第二阶段验收

- CPU、内存和 DeskHud 进程指标来自真实采样，并以受控刷新频率更新。
- 指定应用运行、退出和重新启动时，HUD 不崩溃且能给出正确状态。
- 关闭 HUD、插件或全局开关后不继续进行不必要的高频采样。
- 系统状态（CPU + 内存）、当前应用进程状态与指定应用进程状态 HUD 可独立启用、布局、分组和持久化。
- 三张状态卡使用相同逻辑尺寸和单行 CPU/内存摘要；旧版独立缩放值一次性归一，当前应用卡显示平滑后的实际 HUD 渲染 FPS。
- Windows、macOS、Linux 至少能编译；不支持的单项指标有明确降级行为。

## 第三阶段：便签插件

插件建议命名为 `hud.deskhud.notes`。一个 `note` HUD 定义允许创建多个实例，每个实例
保存自己的内容和样式。

### 3.1 通用动态实例与配置

- [ ] 在第一阶段实例模型上增加 contribution 的单例/可重复实例化声明。
- [ ] 提供新增、复制、删除实例的宿主操作；删除必须精确清理该实例的配置、布局和组成员引用。
- [ ] 定义通用 HUD 配置字段：单行文本、多行文本、布尔值、数字、颜色和枚举。
- [ ] 通过平台无关 `HudFrameCtx` 只向插件传递当前实例的已校验配置、主题和时间，不暴露整份 prefs。
- [ ] 为配置文本、字段数量和单插件实例数量设置合理上限，为未来 WASM HUD ABI 保留可校验形状。

### 3.2 便签功能

- [ ] `note` 实例支持标题、多行正文、背景色、文字色、字号、透明度和标题显示开关。
- [ ] 设置页提供添加便签、编辑、复制、删除和重命名操作。
- [ ] 第一版只在设置页编辑内容；运行态便签保持展示/穿透，不引入桌面就地输入、焦点窗口或额外平台窗口。
- [ ] 文本换行、最大尺寸、超长内容截断/滚动策略在中性 HUD 契约中明确，三平台表现保持可接受的一致性。
- [ ] 每个便签实例可独立布局，也可以作为成员加入 HUD 组并参与排序。
- [ ] 插件和配置字段的用户可见文案全部使用包内 gettext 资源。

### 第三阶段验收

- 用户可以创建至少三个内容和样式不同的便签，重启后完整恢复。
- 复制便签会生成新实例 ID；修改副本不会影响原便签。
- 删除便签不会误删其他实例，并会从所属组中移除对应引用。
- 多个便签可以和系统 HUD 放进同一组，移动、缩放、排序和开关行为正确。
- 超长文本或异常配置不会导致布局无限扩张、渲染阻塞或程序崩溃。

## 明确后置

- HUD 组嵌套、循环或同一实例同时属于多个组。
- 桌面便签直接获取键盘焦点并就地编辑。
- 插件自行创建窗口、操作平台句柄或直接调用 egui。
- 向社区 WASM 开放任意系统、进程、文件系统或网络权限。
- 在原生闭环稳定前完成社区 HUD Guest ABI；后续 ABI 必须复用同一实例、配置和中性帧语义。

## 分阶段验证

每个阶段至少执行：

```powershell
cargo fmt --all
cargo test -p deskhud-engine -p deskhud-ui -p deskhud-runtime
cargo check --workspace --all-targets
cargo clippy --workspace --all-targets -- -D warnings
```

涉及窗口、布局编辑和透明合成的阶段，还需在支持的平台手工验证多显示器、DPI、置顶层级、命中穿透、设置保存与重启恢复。
